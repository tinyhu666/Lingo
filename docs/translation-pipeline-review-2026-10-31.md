# 翻译链路审查与优化：2026-10-31

## 链路

一次快捷键翻译经过这些阶段（客户端 Rust → 代理 Node → 模型）：

1. 全局快捷键触发；Windows 上先等待用户松开修饰键。
2. 写入剪贴板探针，注入 Ctrl/⌘+A、Ctrl/⌘+C，轮询剪贴板直到读到真实文本（最多 1.5 s，Windows 150 ms 后补发一次复制）。
3. 客户端根据文本脚本自动修正方向（目标语言写的句子会反向翻译），POST `/translate`，总预算 15 s，503/429/5xx 与空结果重试一次。
4. 代理：构造系统提示（任务、保真规则、游戏术语、风格、命中的术语表），选择快速通道或主模型，60 s 进程内缓存与并发合并，失败走备用模型链。
5. 写回剪贴板，注入 Ctrl/⌘+A、Ctrl/⌘+V，粘贴后 350 ms 再恢复用户原剪贴板。

2026-10-27 的基线：完整流程 P50 1204 ms、P95 2126 ms，其中模型请求 P50 838 ms、P95 1341 ms，复制和粘贴各约 250 ms / 66 ms。模型这一段占七成，是本次优化的重点。

## 发现的问题

| 位置 | 问题 | 影响 |
|---|---|---|
| 代理 → 模型 | Node 内置 fetch 的空闲连接 4 s 就关闭，游戏聊天是间歇性的，几乎每次都重新握手 TLS | 每次多 50–200 ms |
| 代理 → 模型 | 单次请求，模型偶发的长尾（排队、重试）直接传给玩家 | P95 被少数慢请求拉高 |
| 代理 | `gg` / `wp` / `BKB CD 20` 这类固定短语也要走模型，再由“未改变”校验放行 | 白白等一轮模型 |
| 代理 | `max_tokens` 按长度压得很紧，但没有检查 `finish_reason`，输出被截断时会把半句话粘贴进聊天框 | 准确性问题 |
| 代理 | 模型偶尔带引号、`译文：` 前缀或换行，原样回填 | 聊天框里显示异常 |
| 客户端 → 代理 | 到代理的 HTTPS 连接空闲几分钟后被边缘关闭，静默一段时间后的第一次翻译要重新握手 | 第一次翻译多 100–300 ms |
| 客户端 | 同一句重复喊话仍然走网络（代理缓存只有 60 s，而且仍要一次往返） | 重复喊话每次 800 ms+ |

复制 / 粘贴阶段的目标窗口校验、补发复制、修饰键等待与剪贴板互斥在上一轮已经处理好，本次没有改动。

## 改动

### 代理（`server/translate-proxy`）

- **连接复用**：`upstream-agent.mjs` 用 undici `Agent` 做全局 dispatcher，空闲连接保留 90 s（上限 10 min）。可用 `UPSTREAM_KEEP_ALIVE=false` 关闭。
- **对冲请求**：`model-client.mjs` 中，一次模型调用在 `hedge_after_ms`（默认 1200 ms，`MODEL_HEDGE_AFTER_MS` 或运行时配置可调，0 关闭）后仍未返回时，发一份完全相同的重复请求，谁先回用谁，另一份立即中止。只有慢请求会产生重复，按基线分布约 15–20% 的请求会触发。响应与日志里新增 `hedged` 字段。
- **截断重试**：检查 `finish_reason === 'length'`（Anthropic 为 `stop_reason === 'max_tokens'`），用翻倍的 token 预算（不超过该路由的 `max_tokens`）重试一次；重试失败则保留第一次结果。
- **固定短语直返**：`isInvariantChat` 命中的文本（不含入向翻译）直接以 `response_source: "invariant"` 返回，不调用模型。
- **输出清洗**：`translation-output.mjs` 去掉 `<think>`、首尾包裹的引号、`Translation:` / `译文：` 等标签、换行；引号属于句子内容时保留。所有模型结果在缓存前都会经过这一步。
- **提示词**：中英互译和同语言润色各加一行示例，锚定短句、可直接发送的语气；`PROMPT_REVISION` 升到 `2026-10-31.1`，旧缓存自然失效。
- 空结果重试、备用模型链、快速通道熔断和并发合并逻辑不变；模型调用集中到 `model-client.mjs` 并用假 fetch 做单元测试。

### 客户端（`src-tauri`）

- **本地记忆**：`ai_translator.rs` 增加 128 条、10 分钟的进程内记忆，键包含文本、语言方向、风格、游戏与日常模式。命中时不发请求，日志标记 `source=client-memo`。空结果不记忆。
- **保活**：翻译启用期间每 4 分钟 GET `/healthz`，复用同一个 reqwest 连接池，避免静默后的首次翻译重新握手。

## 验证

- 代理：`npm run proxy:smoke`，含新增的 `model-client.test.mjs`（对冲胜出并中止慢请求、无对冲、预算不足不对冲、主请求失败后由对冲回答、截断重试与上限、空结果重试、统一截止时间）和 `translation-output.test.mjs`；smoke 测试断言固定短语不再调用模型。
- 客户端：`cargo test`，新增记忆命中不发第二次请求、记忆过期与上限、空结果不记忆。
- 以上均为本地与模拟上游的验证，线上收益需要安装新客户端后用 `/admin/translation-diagnostics` 按 `operation_id` 配对统计。

## 后续可做

- 代理日志里已有 `hedged` 与 `response_source`，部署一周后统计对冲触发率与收益，再决定是否把 `hedge_after_ms` 下调到 1000 ms。
- 快速通道（`FAST_MODEL_*`）在生产环境未开启；如果主模型与快速模型相同，开启也不会更快。
- 若要进一步压低首字延迟，可在代理侧启用流式响应并在客户端累积，但对 20 token 以内的短句收益有限。
